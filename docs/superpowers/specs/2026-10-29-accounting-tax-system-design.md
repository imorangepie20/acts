# 회계·세무 시스템 — 기획 / 설계 (Master Design)

- **작성일:** 2026-10-29
- **프로젝트:** `SDTPL_ADM` (기존 shadcn UI Kit 클론 템플릿 위에 개발)
- **상태:** 초안 — 사용자 검토 대기

> 표기: **[결정]** 사용자가 직접 정한 것 · **[제안]** Claude가 정한 기본값(사용자가 뒤집을 수 있음) · **[일반 관행]** 국내 중소기업 회계 실무의 일반적 방식으로 정한 것(사용자 지시: "일반적인 방식으로 정해서 하자") · **[빌더 재량]** 구현자가 정해도 되는 것

---

## 1. 무엇을, 왜 만드는가

중견·중소기업이 **자기 회사 장부를 사내에서 직접 관리**하는 회계·세무 시스템이다.

**현재 상태 [결정]:** 고객 기업들은 영수증·세금계산서를 보고 **엑셀로 장부를 정리**한 뒤 그 자료를 **세무사 사무실에 넘기고**, 신고는 세무사가 한다.

**문제 [결정]:**
- 실무자는 **계정과목 분류**에서 가장 많이 실수한다.
- 경영진은 **지금까지의 재무 상태**를 알고 싶지만, 엑셀 + 세무사 결산 구조에서는 늦게·부정확하게 안다.

**제품 형태 [결정]:** 범용 기본 제품을 만들고, **고객사별로 커스터마이징해서 납품**한다. 납품된 각 시스템은 **한 회사 전용**(single-tenant)이다. 한 시스템 안에 여러 회사를 섞지 않는다.

**성공의 모습 [결정]:** 최고 관리자가 아침에 시스템을 열어 **어제까지의 경영 성과**(손익 + 자금)를 확인하는 순간.

## 2. 목표 / 비목표 / 실패 기준

### 목표
1. 엑셀 장부를 대체하는 전표 입력·장부 관리 (1단계)
2. 계정과목 분류 실수를 줄이는 입력 경험 (1단계)
3. 최고 관리자용 "어제까지" 손익·자금 대시보드 (1단계)
4. 급여 계산과 원천징수 (2단계)
5. 원천세를 회사가 **직접** 신고 (3단계) [결정]

### 비목표
- 한 시스템에 여러 회사를 담는 멀티테넌트 SaaS (납품형이므로 불필요)
- 세무사 업무 대행 범위의 신고(부가세·법인세 직접 신고) — 이건 계속 세무사에게 넘긴다 [제안: 사용자는 "원천세 직접 신고"까지만 목표로 언급]
- 템플릿의 데모 페이지(호텔·크립토 대시보드, AI 앱 등)를 회계 기능으로 억지로 살리는 것

### 실패 기준 (기술적으로 동작해도 실패) [결정]
- **UX가 망가짐:** 실무자가 헤매거나 불편해서 엑셀로 돌아간다.
- **시스템 부하:** 화면이 느리거나 홈서버가 버거워한다.
- **업무 부하:** 엑셀 때보다 실무자가 입력·확인할 일이 늘어난다.

→ 모든 화면 설계에서 "엑셀보다 입력이 적고 빠른가"를 판단 기준으로 쓴다.

## 4. 사용자와 권한 (1단계)

| 역할 | 하는 일 |
|------|------|
| **실무자** [결정] | 영수증·세금계산서를 보고 전표 입력, 증빙 첨부, 추천된 계정과목 확정 |
| **중간 관리자** [결정] | 전표 검토, (승인 기능이 켜져 있으면) 승인/반려 |
| **최고 관리자** [결정] | 경영 대시보드·재무제표 조회. 입력은 하지 않음 [제안] |

**전표 승인 [결정]:** 설정에서 켜고 끈다.
- 꺼짐 → 입력 즉시 장부·대시보드에 반영
- 켜짐 → **승인된 전표만** 장부·대시보드에 반영. 미승인 건수는 관리자 화면에 표시 [제안]

## 5. 1단계 기능

### 5.1 전표 입력 — 분류 실수 줄이기가 핵심

**입력 원천 [결정]:** 영수증과 세금계산서를 보고 사람이 입력한다.

[제안] 입력 부담과 분류 실수를 줄이는 장치:
- **계정과목 추천:** 같은 거래처·비슷한 적요로 과거에 어떻게 분류했는지 보고 계정을 추천한다. 추천의 근거는 **이 회사의 과거 기록만** 사용한다(단일 회사 시스템). 첫 도입 시에는 기본 규칙(예: 거래처 업종·적요 키워드)으로 시작.
- **자주 쓰는 거래 템플릿:** 반복 거래(임차료, 통신비 등)를 저장해 두고 불러오기.
- **전자세금계산서 일괄 불러오기:** 홈택스에서 내려받은 전자세금계산서 엑셀 파일을 업로드 → 거래처·공급가액·세액 자동 채움, 계정만 확인.
- **카드 사용내역 일괄 불러오기 [일반 관행]:** 홈택스 사업용 신용카드 매입내역(또는 카드사) 엑셀을 업로드 → 건별 전표 초안 생성, 실무자는 추천 계정을 **목록에서 한꺼번에 확인·확정**. 카드사·은행 자동 수집(스크래핑)은 1단계 범위 밖.
- **증빙 첨부:** 영수증 사진/스캔 파일을 전표에 첨부, 서버 디스크에 저장.
- **복식부기 강제:** 차변 합계 = 대변 합계가 아니면 저장 불가. 단, 실무자가 차·대변을 직접 다루지 않아도 되도록 **거래 유형 중심 간편 입력**(예: "카드로 비용 지출")을 기본으로 하고, 일반 전표(차·대변 직접 입력)는 보조로 둔다.

### 5.1.1 전표 모델 — 부가세 정보 [제안]

전표는 단순 분개가 아니라 **매입매출 정보를 담을 수 있는 구조**로 만든다. 데이터가 쌓인 뒤에는 바꾸기 어렵기 때문이다.
- 증빙 유형: 세금계산서 / 계산서 / 신용카드 / 현금영수증 / 간이영수증 / 없음
- 과세 구분: 과세 / 영세 / 면세, 매입세액 공제 / 불공제
- 간편 입력은 부가세대급금·부가세예수금을 자동으로 분리한다.
- 통화는 **원화(KRW)만** 지원한다. 외화는 1단계 범위 밖.
- **관리 항목 [일반 관행]:** 전표 각 줄에 **사업장**과 **부서**를 선택 항목으로 둔다(더존 등 국내 회계 프로그램의 표준 구조). 기본값은 사업장 1개, 부서 사용 안 함이며 설정에서 켠다. 처음부터 데이터 구조에 넣어 두어 나중에 데이터 이전이 필요 없게 한다. 모든 장부·재무제표·대시보드에 사업장/부서 필터 제공.

### 5.1.2 전표 수정 정책 [제안]

- 마감 전 전표는 수정·삭제 가능, 모든 변경은 **변경 이력**(누가·언제·무엇을)으로 남긴다.
- 승인된 전표를 수정하면 다시 미승인 상태가 된다(승인 기능 켜진 경우).
- **월 마감**을 1단계에 포함한다. 마감된 달의 전표는 잠기고, 고치려면 관리자가 마감을 해제하거나 당월에 수정 전표를 입력한다.

### 5.1.3 도입 시 기초잔액 [제안]

연도 중간에 도입하는 회사는 **기초잔액**(계정별·거래처별 잔액)을 입력해서 시작한다. 기존 엑셀 장부 전체를 일괄 불러오는 기능은 1단계 범위 밖.

### 5.2 장부와 재무제표 [제안]
- 일반 전표 목록 / 분개장
- 계정별 원장, 거래처별 원장
- 합계잔액시산표
- 손익계산서, 재무상태표 (기간 지정, 전기 비교)
- 엑셀 내보내기 (모든 장부)

### 5.3 최고 관리자 대시보드 [결정: B안 "손익 + 자금"]
기준 시점은 **어제 마감**.
- 이번 달 누적 영업이익
- 현금·예금 잔액
- 미수금(받을 돈), 미지급금(줄 돈)
- 월별 손익 추이 (올해)
- 재무상태 요약: 자산 · 부채 · 자본

(시안: `.superpowers/brainstorm/` 의 `ceo-dashboard.html` B안)

### 5.4 세무사와 자료 주고받기 [일반 관행]

국내 세무사 사무실 대부분은 **더존 Smart A**(일부 세무사랑)를 쓴다. 이에 맞춘다.

- **계정과목 코드:** 더존 표준 계정코드 체계(예: 101 현금, 103 보통예금, 108 외상매출금, 251 외상매입금, 401 상품매출, 8xx 판매비와관리비)를 기본 계정과목표로 쓴다. 세무사 쪽 프로그램과 코드가 같아 옮겨 적을 때 실수가 줄어든다.
- **내보내기(회사 → 세무사):** 기간 지정 후 엑셀로 내려받는다 — 분개장(계정코드 포함), 합계잔액시산표, 매입·매출 세금계산서 목록, 카드·현금영수증 매입 목록(부가세 신고용), 증빙 파일 묶음(zip). Smart A 업로드 양식과의 정확한 일치는 첫 고객사의 세무사와 확인 후 맞춘다.
- **결산 반영(세무사 → 회사):** 세무사가 연말 결산 후 넘겨주는 결산 수정 내역(감가상각, 대손, 미지급비용, 법인세 등)을 실무자가 **결산 전표**(전표 유형 '결산')로 입력한다. 결산 전표는 대시보드에서 따로 구분해 볼 수 있다.
- **연도 이월:** 결산 후 재무상태표 잔액을 다음 해 기초잔액으로 이월하는 기능을 1단계에 포함한다. 이월 결과가 세무사 신고 재무제표와 일치하는지 확인할 수 있게 한다.

### 5.5 설정 (회사별 커스터마이징 지점)
- 회사 기본 정보, 회계연도
- 계정과목표 — 더존 표준 코드 기반 기본표 제공, 회사별 추가·수정·숨김
- 사업장·부서 사용 여부와 목록
- 전표 승인 사용 여부 [결정]
- 사용자·역할 지정
- 거래처 관리

**커스터마이징 원칙 [제안]:** 고객사별로 달라지는 것은 **설정·데이터로 표현**하고, 코드 분기(고객사별 포크)는 최후 수단으로 한다. 고객사가 늘어도 공통 제품 하나를 유지보수하기 위해서다.

## 6. 기술 구성 [제안 → 사용자 승인]

| 항목 | 선택 |
|------|------|
| 앱 | 기존 템플릿 **Next.js 16 풀스택** (화면 + 서버 로직, 별도 백엔드 없음) |
| DB | **PostgreSQL** — 전표 차·대변 원자적 저장(트랜잭션), 금액은 정확한 숫자 타입(`numeric`), 부동소수점 금지 |
| 인증 | 시스템 자체 계정 로그인 — **로그인 ID는 이메일** [결정] + 역할 기반 권한 (외부 인증 서비스 없음), 로그인 실패 횟수 제한·계정 잠금 |
| 접속 [결정] | **Cloudflare Tunnel**로 `https://acts.approid.team` 공개 (TLS는 Cloudflare에서 처리, 보안 쿠키 사용). 앱·DB 포트는 서버 밖으로 열지 않음. 추가 보호로 Cloudflare Access(허용 이메일) 권장 [제안]. 2단계(주민등록번호·급여 저장) 착수 시 2단계 인증과 민감정보 암호화를 추가 |
| 파일 | 증빙 이미지는 서버 디스크 저장 |
| 배포 | **Docker Compose** (앱 + DB + cloudflared), 서버 `approid@192.168.219.174` (Zorin OS 홈서버), 원격 저장소 `https://github.com/imorangepie20/acts.git` [결정] |
| UI | 템플릿의 shadcn/ui(Base UI) 컴포넌트·레이아웃·대시보드 패턴 재사용, 폰트 Pretendard, 화면 언어 한국어 |

[빌더 재량] ORM, 인증 라이브러리, 마이그레이션 도구, 파일 저장 경로 구조.

### 템플릿 처리 [제안]
- 사이드바·⌘K 팔레트(`src/lib/nav.ts`)를 회계 메뉴로 교체한다.
- 데모 페이지는 메뉴에서 빼고, `/components/*` 쇼케이스는 개발 참고용으로 당분간 남긴다. 최종 납품 전 제거.
- 기존 e2e 스모크 테스트(`allNavItems` 전 라우트 렌더)는 새 메뉴 기준으로 계속 동작해야 한다.

## 7. 성능·운영 기준 [제안]
- 홈서버 한 대 기준. 대상 규모: 중견·중소기업 1개사, 동시 사용자 수십 명 이하, 연간 전표 수만~수십만 건.
- 대시보드·재무제표는 전표 수가 늘어도 수 초 안에 열려야 한다 → 잔액 집계 방식(실시간 합산 vs 일 마감 집계)은 빌더가 측정 후 결정.
- DB 정기 백업 (회계 데이터 유실은 치명적).
