## Project

`acts` — a Korean accounting system (Phase 1A foundation + auth + admin; Phase 1B chart of accounts, partners, sites/departments, vouchers with VAT, approval, history, evidence attachments; Phase 1C ledgers and statements: 분개장, 계정별/거래처별 원장, 합계잔액시산표, 손익계산서, 재무상태표, Excel export; Phase 1D executive dashboard, month close, opening balances, 결산 vouchers, year close; Phase 1E account recommendation, transaction templates, 홈택스/카드 xlsx/xls imports, tax lists and the 세무사 ZIP package; Phase 2 payroll: employees, 급여 대장 runs, 4대보험/간이세액 calculation, payslips, payroll vouchers, mandatory 2FA; Phase 3 원천세: 원천징수이행상황신고서 screen and 근로소득 간이지급명세서 file; VAT: 부가가치세 신고 자료 screen and Excel) on Next.js 16 (App Router) + React 19 + Tailwind v4 + shadcn/ui using the **Base UI** primitives (`@base-ui/react`, shadcn style `base-nova`), not Radix. Postgres via Drizzle ORM. The project started from the shadcnuikit.com template; its mock dashboard/apps/showcase pages were removed (they are in git history before the template cleanup).

## Commands

Package manager is **pnpm**. Ports: app 3710, Postgres 5710 (override with `APP_PORT` / `DB_PORT` in `.env`).

```bash
docker compose up -d db  # dev database only (prod services are under profile `prod`)
pnpm db:migrate          # apply Drizzle migrations (drizzle/)
pnpm db:seed             # idempotent; creates admin from ADMIN_EMAIL / ADMIN_PASSWORD (refuses empty / "change-me-now"), the Douzone-style standard chart and the `본점` site (runs on every deploy via the `migrate` service)
NEW_PASSWORD=... pnpm admin:reset-password <email> [--reset-2fa]  # reset password, clear lock, drop sessions (--reset-2fa also removes the TOTP enrolment)
pnpm dev                 # dev server at http://localhost:3710
pnpm build               # production build (does NOT run lint)
pnpm lint                # eslint — run separately from build
pnpm test                # vitest (needs the db up)
pnpm test:e2e            # Playwright, all specs

pnpm exec playwright test e2e/auth.spec.ts      # single spec file
pnpm exec playwright test -g "title fragment"   # single test by title
```

Local `.env` must set `ADMIN_PASSWORD` (non-default, >= 8 chars) and `COOKIE_SECURE=false` (plain-http dev/e2e; `.env.example` leaves both out so production defaults to secure cookies). `ADMIN_PASSWORD` is only used on the first seed. It also needs `PAYROLL_ENCRYPTION_KEY` (`openssl rand -base64 32`): payroll and manager/admin 2FA login need it, and losing it makes stored 주민등록번호/계좌/TOTP secrets unreadable (back it up apart from DB dumps).

Playwright's `webServer` runs `pnpm db:migrate && pnpm db:seed && pnpm build && pnpm start` on :3710, so tests hit a **production build**. Locally it reuses a server already on :3710 — if `pnpm dev` is running, tests run against dev instead (and a stale server means stale code).

Deploy: `docker compose --profile prod up -d --build` (db, migrate, app, cloudflared) on the server; `scripts/backup.sh` for Postgres dumps plus an uploads-volume archive. See `docs/deploy.md` (Korean). `next.config.ts` uses `output: "standalone"`.

## Architecture

- **Route groups:** `src/app/(dashboard)` wraps pages in the app shell (`SidebarProvider` + `AppSidebar` + `AppHeader`); `src/app/(auth)` uses a bare centered layout. `/` redirects to the role's home (staff → `/vouchers`, others → `/overview`).
- **`src/lib/nav.ts` is the sitemap.** `navGroupsFor(role)` (items carry a `permission`) drives the sidebar *and* the ⌘K command palette, and `allNavItems` drives `e2e/smoke.spec.ts`, which renders every route and fails on HTTP ≥400 or uncaught page errors. Adding a route means adding it here.
- **Server layering.** Domain services in `src/server/<area>/service.ts` take `db` first and return a `Result` (`src/server/result.ts`). Pages and actions go through `src/server/auth/dal.ts` (`verifySession`, `requirePermission`); `src/proxy.ts` is only an optimistic cookie check. The permission matrix is `src/lib/permissions.ts`. Tests: Vitest runs against the real `acts_test` DB (`tests/helpers/db.ts`); e2e uses a stored admin session from `e2e/auth.setup.ts`. Vitest tests get reference data from `seedReference(db)`; Playwright projects: `chromium` (app specs, incl. `imports.spec.ts` and `exports.spec.ts` for Phase 1E), then `settings-serial` (`admin.spec.ts`) → `settings-serial-payroll` (`payroll.spec.ts`) → `settings-serial-withholding` (`withholding.spec.ts`) → `settings-serial-approval` → `settings-serial-closing` (`closing.spec.ts`, serial, fiscal year 2000 only) run the specs that change shared state.
- **Reports aggregate posted lines on the fly** (no summary tables); at a 500k-line year the statements take ~150 ms, journal page 1 ~0.5 s, and the account-ledger page ~0.4 s because the page is paged 1,000 lines at a time (`getAccountLedger(..., { page })`; unpaged = full ledger for Excel). Perf test: `PERF=1 pnpm test src/server/reports/perf.test.ts`.
- **Thin pages, fat feature folders.** `page.tsx` files only compose components. Each feature lives in `src/components/<area>/` (vouchers, reports, payroll, imports, admin, auth, …), plus:
  - `src/components/layout/` — sidebar, header, breadcrumbs, command palette, user menu (내 정보 → `/profile`, 로그아웃), theme
  - `src/components/ui/` — shadcn/ui primitives (generated; add via the shadcn CLI per `components.json`; some are unused since the template cleanup)
- **Vouchers** (`src/server/vouchers/`, `src/lib/vouchers/`): a voucher is a header plus >= 2 lines. The three transaction-type forms go through the pure builder `src/lib/vouchers/simple.ts` (`buildSimpleVoucher` / `toSimpleInput`); the service re-validates non-general vouchers by rebuilding them. A trade's optional `splits` (계정 나누기) posts one invoice to several main accounts in order (first = `mainAccountId`, sum = |supply|; refused on a non-deducted purchase with VAT); `toSimpleInput` recovers them from the main-side lines before the VAT line. The VAT return still classifies a purchase as 고정자산 by its first line. **Posted rule:** only `status = 'approved'` counts (`POSTED_STATUSES`); turning approval off auto-approves pending vouchers. Every voucher write adds a `voucher_history` row in the same transaction (`snapshot.ts`). Numbering is per date under an advisory lock; updates use an optimistic `version`.
- **Reports** (`src/server/reports/`: `totals.ts`, `service.ts`, `ledgers.ts` run the SQL aggregation of posted lines; pure builders live in `src/lib/reports/`). Balance-sheet groups accumulate from the beginning of time, P&L groups from the fiscal-year start (`company.fiscalYearStartMonth`); profit from earlier fiscal years shows as the computed equity row `이월이익잉여금(전기 손익)` permanently, because year close posts no carry-forward voucher. Site and department filters apply per line. Report URLs use `from`/`to`/`site`/`dept` (plus `account`/`partner`/`page`), parsed by `parseReportParams`; Excel files come from `GET /api/exports/[report]` (exceljs).
- **Closing** (`src/server/closing/`): month close is a watermark ("closed through M", `period_closes`). Every voucher write (create, update, delete, approve, reject, attach, detach) first takes the global advisory lock `(PERIOD_LOCK, 0)` shared, then company FOR SHARE, the voucher row, then numbering; close and reopen take it exclusive. Opening balances are exactly one `kind = 'opening'` voucher on the cut-off date, and regular vouchers must be dated after it. Year close creates NO voucher: balance-sheet balances roll forward because reports accumulate from the beginning of time; it only locks and reconciles against the 세무사's figures. 결산 vouchers are `kind = 'closing'` ordinary adjusting entries.
- **Dashboard** (`/overview`, `src/server/dashboard/`): data as of yesterday. Cash, receivable and payable totals come from `accounts.dashboard_role`, not codes; the trend comes from `accountTotalsByMonth`.
- **Recommendation** (`src/lib/recommend.ts`, `src/server/recommend/`): suggests accounts from this database's own voucher history, then a keyword fallback table (account codes are data there, resolved at runtime; missing or inactive codes are skipped). Never suggests an inactive account.
- **Templates** (`src/server/templates/`, `voucher_templates`): saved transaction-type forms (max 200), applied from the template menu in `src/components/vouchers/`; `voucher:create` permission.
- **Imports** (`/imports`, `src/lib/imports/`, `src/server/imports/`): pure parsers for 홈택스 tax-invoice and card files, matched by header name (spaces and a `(원)` suffix ignored). `read-xlsx.ts` reads `.xlsx` with exceljs and legacy `.xls` / HTML-table `.xls` with SheetJS (`xlsx`, installed from the cdn.sheetjs.com tarball, not npm); cached formula results only, max 5 MB / 1,000 rows. 홈택스 card files have no 승인번호, so `사업용신용카드거래내역일련번호` is the dedup key. `voucher_imports` is the dedup key (re-importing a row is rejected), and every row is committed through `createVoucher`, so approval status, period lock and numbering apply as for typed vouchers.
- **Exports** (`/exports`, `src/server/exports/`): tax lists (`tax-lists.ts`) and the 세무사 ZIP package (`package.ts`, built with `archiver`) from `GET /api/exports/tax-package`; posted vouchers only, `export:tax` permission. The 1C report keys on `/api/exports/[report]` keep `ledger:view`.
- **Payroll** (`/payroll/*`, `src/lib/payroll/` pure calc/bonus/rrn/voucher builders, `src/server/payroll/` employees, items, settings, runs, rates, 급여 대장 Excel): `payroll:manage` (manager, admin). **No rate or table in code:** 요율/상·하한 live in `payroll_rates` and the 간이세액표 in `withholding_tables`, loaded by the seed from `src/server/payroll/seed-data/` (each value carries its source URL; the one unconfirmed rule, the order of the 80/120% rate vs the month count for 상여, is marked `// UNVERIFIED` in `src/lib/payroll/bonus.ts`); the calc functions take them as arguments. The two 사업주-only kinds, `employment_stability_company` (고용안정·직업능력개발, 고용보험 가입자) and `industrial_accident_company` (산재, every non-임원 via `insIndustrialAccident`), are company-specific: not seeded, entered on 급여 설정 (사업주 부담 요율, `src/lib/payroll/employer-rates.ts`), 0 without a row; both go to the 고용보험 base, the 811 debit and the 근로복지공단 credits (산재 as its own line). **Lookup dates:** 4대보험 rates use the 귀속월 1일, the 간이세액표 uses the run's 지급일, both the latest `effective_from <=` that date. Two 간이세액표 revisions are seeded (2024-03-01, 2026-03-01; only the child credit differs). 장기요양 is premium-based (floor10(건강보험료 × ltc%), 13.14% in 2026), not salary-based. Every insurance amount and 지방소득세 is floored to 10원; the table amount is used as-is. Run states are draft → confirmed: `confirmRun` refuses when rates, table or bonus basis moved since the last calc (so the UI has a 재계산 button) and writes one `kind = 'payroll'` voucher through `writePayrollVoucher` under the usual lock order; that voucher refuses edit/delete/attach/detach (`ERR_PAYROLL_ONLY`) and is changed only by 확정 취소 in the 대장. Approving or rejecting it needs `voucher:approve` **and** `payroll:manage`. **Visibility:** users without `payroll:manage` (`hidesPayroll(role)`) see payroll vouchers as a hidden row (`급여 전표`) in the list and not at all in the journal and ledgers (`ReportFilter.hidePayroll`, set from the user, never the URL; `countHiddenPayroll` feeds the ledger notice); statements, the dashboard and closing still count them. **Secrets:** 주민등록번호 and account numbers are encrypted (`src/server/crypto/secret.ts`, `PAYROLL_ENCRYPTION_KEY`) with an HMAC for the duplicate check; lists, the 대장 and Excel show masked forms only, and 보기 goes through `revealEmployeeSecret`, which writes an audit row.
- **Withholding** (`/payroll/withholding`, `/payroll/simplified-statement`, `POST /api/payroll/simplified-statement`, `src/lib/withholding/` pure builders, `src/server/withholding/` loaders; `payroll:manage`): confirmed runs only. The 신고서 (별지 제21호) is a reference screen plus Excel for 홈택스 entry and fills only A01/A10/A99 (other rows show `이 프로그램에서 계산하지 않음`); it aggregates on the **지급 basis** (지급일 month, optional 귀속월 filter, ⑫ 전월 미환급세액 typed in the URL as `refund`), while the 간이지급명세서 file aggregates on the **귀속 basis** (귀속월 in the half-year). The file is fixed-length 190-byte EUC-KR records plus CRLF, written with iconv-lite and a strict KS X 1001 check (characters outside it, control characters or a blank name refuse the download); the layout is the NTS 2021 상반기 전산매체 spec and is **홈택스 검증 전** (never worded as verified; the page and dialog say so). The file name is `SC` + 사업자등록번호 digits 1-7 + `.` + digits 8-10; company filing fields (세무서코드, 사업자 유형, 법인등록번호, 홈택스 ID, 담당자) live on the company form. The plain 주민등록번호 exists only inside the downloaded file (each download writes a reveal audit row per employee); an individual business's 대표자 주민등록번호 is typed in the dialog, POSTed, and never stored or logged. `payroll_items.exclude_from_total_paid` (true for `car`) keeps 비과세 자가운전보조금 out of 총지급액 (lines confirmed before Phase 3 recompute that exclusion from the current item settings).
- **VAT** (`/exports/vat-return`, `GET /api/exports/vat-return`, `src/lib/vat/` pure periods/rows/builder/notices, `src/server/vat/` entry loader, view and Excel sheets; `export:tax`): approved 매입·매출 vouchers of one 신고기간 (예정 = first quarter of the 기, 확정 = last quarter, or the whole 기 without a 예정신고) filled into the rows of 별지 제21호서식 <개정 2026. 3. 20.> (제1쪽 (1)–(35), 제4쪽 (36)–(90); `COMPUTED_VAT_ROWS` lists what acts fills, every other row shows `NOT_COMPUTED_TEXT`, shaded cells stay empty), plus 매출처별/매입처별 세금계산서합계표(갑) and 신용카드매출전표등 수령명세서(갑). 전자 외 발급분 comes from the voucher's `paper_tax_invoice` flag and ⑧ 그 밖의 신용카드 from `unregistered_card` (both switches on the trade form). Excel has four sheets (`신고서`, `매출처별 합계표`, `매입처별 합계표`, `신용카드 수령명세서`) and is built even for an empty period. Labels and order are **not verified against 홈택스** (`VAT_SOURCE_NOTICE`; never word it as verified).
- **Auth / 2FA:** manager and admin must enrol TOTP (others may from the profile). The session carries `mfa_verified`; `verifySession` sends an unverified session to `/2fa/verify` or `/2fa/setup`. TOTP secrets are encrypted with the same `PAYROLL_ENCRYPTION_KEY`, so without it managers and admins cannot log in. `NEW_PASSWORD=... pnpm admin:reset-password <email> --reset-2fa` removes the enrolment.
- **Uploads:** evidence files live under `UPLOAD_DIR` (default `./uploads`, Docker volume `acts_uploads`), the type is sniffed from content, and they are served by `src/app/api/attachments/[id]/route.ts`. `next.config.ts` raises `serverActions.bodySizeLimit` and `proxyClientMaxBodySize` to 11mb (`proxy.ts` runs on Server Action POSTs and would truncate at 10MB).
- Theme: `next-themes` with class strategy (light/dark/system); tokens in `src/app/globals.css`.

## Gotchas

- **Base UI, not Radix.** Composition uses the `render` prop, not `asChild` (exception: the vaul-based Drawer still uses `asChild`). When a `<Button>` renders a link (`render={<Link … />}`), pass `nativeButton={false}` — `e2e/no-base-ui-warnings.spec.ts` guards against the warning.
- **2FA (TOTP) is mandatory for manager and admin** (`mfaRequired`, `src/server/auth/mfa.ts`); `verifySession` sends an unverified session to `/2fa/verify` or `/2fa/setup`. E2E logins go through `e2e/helpers/login.ts`, which keeps each user's secret in `e2e/.auth/totp-<email>.txt`; if you delete `e2e/.auth/`, also run `pnpm admin:reset-password <email> --reset-2fa` so setup enrols again.
- ESLint downgrades `react-hooks/set-state-in-effect` to a warning on purpose (SSR mount guards like `src/hooks/use-mobile.ts`).
- Work is organised in phases; design specs are in `docs/superpowers/specs/` and phase plans in `docs/superpowers/plans/`. E2E specs are named per feature (`vouchers.spec.ts`, `payroll.spec.ts`, …).
